# Case study: a latency fix that quietly broke retrieval

A reproducible before/after investigation on a real RAG corpus, generated by
[`examples/release_check_demo.py`](../examples/release_check_demo.py).

**Setup.** 10,000 passage chunks from "RAG Dataset 12000" (Neural Bridge AI, Apache-2.0;
passages from Falcon RefinedWeb, ODC-By 1.0), embedded with all-MiniLM-L6-v2 and indexed
as IVF-Flat (250 lists, inner product). 300 real questions, each labelled with the chunks of
the passage it was written for. Production searches with `nprobe = 16`, k = 10. Policy:
recall, nDCG and ANN recall may drop by at most 0.02; p95 latency may at most double.

## Pull request 1: "lower nprobe to cut latency"

| | main (nprobe 16) | PR (nprobe 2) |
|---|---|---|
| nDCG@10 | 0.675 | 0.498 |
| Recall@10 | 0.664 | 0.474 |
| ANN recall@10 | 0.883 | 0.544 |
| p95 latency | 1.00× | 0.55× |

**Verdict: fail.** Latency fell 45%, which is what the author measured. But relevance fell
by a quarter, which nobody would have seen without labelled queries.

Diagnosis, as the report states it:

- *verified*: the index finds fewer of its exact nearest neighbours (ANN recall
  0.883 → 0.544).
- *verified*: 1,015 exact neighbours that main found were missed by the PR, all in inverted
  lists the search did not probe (352 other misses predate the change). **nprobe 14 reaches
  95% of the neighbours main found.**
- *supported*: the loss coincides with the configuration change `nprobe: 16 → 2`.

## Pull request 2: "apply the suggested nprobe"

| | main (nprobe 16) | PR (nprobe 14) |
|---|---|---|
| nDCG@10 | 0.675 | 0.674 |
| ANN recall@10 | 0.883 | 0.869 |
| p95 latency | 1.00× | 0.93× |

**Verdict: pass.** A 7% latency saving with no measurable relevance loss. The check also
reports, honestly, that ANN recall dipped by 0.014: inside the policy, and visible.

## Pull request 3: "compress vectors to save memory"

Switching to IVF-PQ with 8 bytes per vector:

| | main | PR (IVF-PQ, 8 bytes) |
|---|---|---|
| nDCG@10 | 0.675 | 0.443 |
| ANN recall@10 | 0.883 | 0.401 |

**Verdict: fail.** The diagnosis separates this from PR 1: the 1,445 newly missed
neighbours were **in probed lists but ranked out by compressed distances**. Raising nprobe
will not recover them; re-ranking with exact distances or more bytes per vector will.

## Why this matters

Each change was locally reasonable and each was "measured": PR 1's latency gain was real.
What a release check adds is the other half of the trade-off, on the queries your users
ask, with a cause attached: which knob, how far, and whether turning it back is the fix.

Reproduce it:

```bash
uv run python examples/release_check_demo.py --out release-check-demo
```

Latency ratios vary by machine; the quality numbers are deterministic for a given seed.
